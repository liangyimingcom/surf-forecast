# 自迭代闭环 · 治理模型 v5（人主导 · 不打断既定开发）

> 背景：v4 设计把闭环做成"能自主写生产的第二写者"，与既定 Kiro 5-spec 开发抢方向盘（双写者撞车 / 冻结E2E 与主动开发对立 / 两个 backlog / 版本流污染）。
> v5 据此**重新定性**：自迭代系统降级为**人主导的生产力助手**，从架构上消除撞车。本文覆盖 v4 中 Q4/Q8 的相反决策。

## 一、五条定性决策（本轮敲定）

| # | 决策 | 覆盖/取代 |
|---|------|-----------|
| G1 | **pipeline = 人主导辅助工具**：AI 只起草 draft PR，由人按自己节奏审并合；**去掉无人值守自动合并/自动部署** | 推翻 v4 Q4(真无人值守) |
| G2 | **建议入口常开**：生产 `/api/feedback` + 💡澄清 UI 持续可用，用户随时提 | — |
| G3 | **每天 triage 仪式**：每日定时（MeshClaw cron）拉队列+垃圾/去重预过滤→推摘要给人→人在对话 accept/reject | 取代 v4 Q8(每条即时发) |
| G4 | **accepted 按风险分流**：琐碎纯前端小改（文案/示例/筛选类）→ 直连 draft PR；触碰功能逻辑/引擎/DATA CONTRACT → **升格为 Kiro spec 任务**走既定流程 | — |
| G5 | **直连 vs 升格 = 人工标注 + 硬规则兜底**：triage 时人标 lane；**直连的 diff 必须过确定性硬门**（⊆ 路径白名单 + 非删除 + 不碰 wdeg/契约关键字），任一不满足 → 强制退回升格。人判意图、机器守边界 | 落实"『纯前端』绝不只凭判断"红线 |

## 二、由此消解的原冲突（为何不再打断既定开发）

- **双写者撞车 → 消失**：pipeline 不再自主写生产/合 master；所有合并由人在既定节奏下做，单一驱动器。
- **冻结E2E vs 主动开发 → 消失**：不再有"无人值守自动门"依赖冻结基线；你照常自由改 E2E 做新功能。
- **两个 backlog → 归一**：feedback 不是旁路产线；动逻辑的一律升格进 Kiro spec，战略路线仍是唯一真相源；只有琐碎小改走助手直连（且受硬门约束）。
- **版本流污染 → 缓解**：无即时发；小改随人的发布节奏搭车，不再每条一个版本。

## 三、运行形态（收尾）

1. **回到既定开发**：主线仍是 Kiro 5-spec（analyzer / web / accuracy-feedback / deployment / custom-spots）。自迭代系统退居后台辅助，不占主驱动。
2. **每日 triage cron**（G3 实现）：`tools/review_queue.py` 包一个 MeshClaw 日常 cron（stdlib、只读拉队列+预过滤→`send_message` 推摘要；**不自动改 status**）。人看摘要后在对话里授权 accept/reject。
3. **accepted 处理**（G4/G5）：
   - 标 `直连`：`req_pipeline.py` 出 draft PR（硬门兜底；过→PR 待你合，不过→自动退回升格）。
   - 标 `升格`：人把它写进对应 spec 的 requirements/tasks，进既定排期。
4. **发布**：沿用 Phase 0 地基（版本 tag / rollback / 金丝雀 / CHANGELOG），由人在既定节奏触发；无自动部署。

## 四、保留不变的红线
GMT+8 / DATA CONTRACT wdeg / float→Decimal / 全 401 / ALB SG 禁 0.0.0.0/0 / terraform 禁 -auto-approve / 单一驱动器 / AI 绝不自动合并 master 或自动部署 / CodeLens 仅后端 / 新表需任务角色按 ARN 授权。

## 五、范围外（明确不做）
无人值守自动部署 / pipeline 自主节奏 / 匿名触发合并 / 「是否纯前端」纯 AI 判定 / feedback 绕过 spec 改核心逻辑。

## 六、实施计划（落地 v5 尚缺的工作）

> 排序原则：**最可能被调整的决策放最前**（决策 → 数据模型 → 新接口 → 用户可见），**机械性重构/测试垫底**。
> 每层动手前先与人确认上一层无异议；单一驱动器，真发布留 G 门。已建：review_queue(A)/req_pipeline(D)/audit_trace/每日 triage cron。缺的是把它们按 v5 的"分流 + 硬规则兜底"串成人主导闭环。

### L0 · 待拍板的决策（最可能改，动手前先确认）
- **D-a 分流硬规则清单**：`direct`(直连) lane 允许改的范围 = 仅 `web/浪报MVP.html`；**禁触碰的契约关键字**清单（`wdeg/tp2/tp/tideEvents/times/windows/hs/wind/gust/_to_decimal/DATA CONTRACT/__SF_READY__`）——命中即强制退回升格。← 需你敲定清单
- **D-b 升格目标映射**：`promote` 的建议进哪个 spec 的 requirements/tasks、用什么最小模板（新 task 行 vs requirement 追加）。
- **D-c lane 记录方式**：feedback 加 `lane` 字段落库，还是 triage 时口头指示我执行、不落字段。
- **D-d triage 摘要渠道**：dashboard-only（默认）/ +Slack。

### L1 · 数据模型 / 契约变更（次高调整可能）
- **M-a** feedback 需求对象扩展：`lane`(direct|promote)、`spec_ref`、`decided_gmt8`（代码契约变；DynamoDB 无 schema 但 review_queue+pipeline 须一致，写入仍走 `_to_decimal`）。
- **M-b** `docs/requirement-schema.md` 同步上述字段；status 状态机补 `promoted`（升格后不进直连队列、不被 TTL 清）。

### L2 · 新接口 / 类型
- **I-a** `review_queue.py` 加 `promote <id> --spec <name>`（写 spec_ref、status→promoted）与 `mark <id> --lane direct`（标直连）。
- **I-b** `req_pipeline.py` 加 `--from-queue <id>`（读生产 accepted 需求，取代当前 seed json 入口）；lane-aware。

### L3 · 用户可见变动
- **U-a**（可选）认领码 `track` 状态文案扩展：新增「已受理/已升格排期/已上线」，让提交者看得到进展（复用现有 GET /api/feedback/track，仅扩状态映射）。
- 说明：治理以内部流程为主，用户可见面小；此项低优先。

### L4 · 内部逻辑（无用户可见面）
- **P-a** `req_pipeline` 硬规则兜底：`direct` lane 的 diff 若碰非白名单文件或 D-a 契约关键字 → **自动退回 `promote` + 通知**，不产出直连 PR（人判意图、机器守边界）。

### L5 · 机械性重构 / 测试补齐（最后）
- **T-a** 单测：lane 判定 / 兜底退回 / promote 流转（阈值双侧钉死 + mutation）。
- **T-b** `review_queue ↔ req_pipeline` 串联集成测试（内存 store，不碰生产）。
- **T-c** README / 文档收口；tools/crons 镜像同步校验。

> 注：产品主线（Kiro 5-spec：analyzer/web/accuracy-feedback/deployment/custom-spots）是**独立路线**，各自 tasks.md 跟踪，不在本实施计划内；本计划仅补齐"自迭代辅助工具"的人主导闭环。

### 执行注意（把本计划当 goal 跑时的硬约束）
1. **L0 是人工决策门，loop 不得逾越**：loop 到 L0 只能"产出提案 + 停下等人批"，**绝不自行拍板默认值**当既定事实推进（否则违背 v5 人主导）。决策未定 → 创建 STOP，不空转。
2. **测试随层编织，不适用"机械最后"**：本项目红线要求分级/阈值/lane 判定**边界双侧钉死 + mutation**。故 lane 判定/兜底(L4) 的单测**与该层同步写**，不推迟到 L5；L5 只放纯集成串联+文档收口。排序原则（决策优先）仍成立，但"测试垫底"对红线覆盖的逻辑**例外**。
3. **M-a/M-b 触碰已上线 feedback 契约 = 非回滚**：加 `lane/spec_ref` 改的是**生产在写的数据形状**；读路径必须容忍旧行缺字段（默认值），写仍走 `_to_decimal`；此层按"含数据变更不可回滚"对待，只前向修复。
4. **自食风险**：每日 triage cron(8e721bb9) 在跑并调用 `review_queue.py`；改其 schema/接口期间，须保证 cron 读路径向后兼容（旧字段缺省不报错），避免"边建边崩"live cron。
5. **单一驱动器**：本 goal 与每日 cron、任何产品主线 goal 不并发写同一文件；同一时刻只一个驱动器。
